# Contract for S1–S6 (server/web) ↔ M2–M5 (Mac) — 2026-10-20

Both sides build against exactly this. Existing behaviour not mentioned stays as is.
Repo: /workspace/fairplay (branch student-app-2026-10-13). Server tests: venv /tmp/fpvenv
(`cd server && /tmp/fpvenv/bin/python -m pytest -q`). Web: `cd web && npx vitest run && npx tsc --noEmit -p .`.

## Version and time headers (S2 / M5)
- Every `/api/*` response carries `X-Server-Time: <ISO-8601 UTC with ms, ending Z>`.
- Apps send on every request they make (native or via the page): `X-FairPlay-Version: 0.5`
  and `X-FairPlay-Platform: mac` (or `windows`).
  - The page learns both from the bridge: the app's `state` message gains `app_version` and
    `platform`.
  - The web API client adds the two headers to every `/api` request when the bridge has
    reported them.
- Server config (env): `MIN_APP_VERSION_MAC`, `MIN_APP_VERSION_WINDOWS`. Default `""` means
  no minimum.
- Versions compare numerically by dot-separated parts: 0.10 > 0.9, 1.0 == 1.0.0.
- `POST /api/student/exams/{id}/start` and `POST /api/student/attempts/{aid}/app-beat`:
  - If the platform header is present and the version is below that platform's minimum:
    `426 {"detail": "Update FairPlay to continue", "min_app_version": "<min>"}`.
    No header means no gate (a browser without the app).
  - Their JSON gains `server_time` (ISO, same format) and `min_app_version` (string or null).
- New `GET /api/app/version` (no auth) → `{"mac": "<min or null>", "windows": "<min or null>", "server_time": "..."}`.
  `/api/health` keeps working with no gate.
- Web: a 426 anywhere shows a full-page "Update FairPlay" screen with the minimum version.

## Device check (S1 / M2)
- Bridge: the page posts `{action:"preflight"}`. The app answers
  `{type:"preflight", problems:[...strings, unchanged...], checks:[{id, ok, message, info}], platform, app_version, os_version}`.
  - `problems` stays for older pages and Windows.
  - `info: true` marks informational rows that never block (VPN, battery).
- Check ids (Mac):
  - `macos_version`, `app_version`, `clock`, `server`, `vpn`, `displays`, `blocked_apps`,
    `input_source`, `disk`, `battery`, `accessibility`.
  - Also any existing problem the app knows (`vm`, `sharing_ports`, …), which may use its own id.
- `POST /api/student/device-check` (student auth). Body:
  `{platform, app_version, os_version, checks:[{id, ok, message, info?}], exam_id?: string|null}`
  (at most 40 checks, strings at most 300 chars).
  Response `{ok:true, saved_at}`. Stores the latest report per (student, platform).
- `GET /api/exams/{exam_id}/readiness` (teacher who owns the exam). One row per student in
  the exam's class; if there is no class, the students who have attempts:
  `{student_id, name, platform, app_version, os_version, ok (all non-info checks ok), failed:[ids], checked_at}`,
  or `null` fields if never checked.
- Web:
  - Readiness page: a "Run check" button calls preflight, shows the rows and POSTs them.
  - Fix the "Running in the FairPlay Mac app" text to name the platform correctly.
  - Teacher exam page or live room: a "Device readiness" list.

## Clock (M5, app-only rule)
The app compares `X-Server-Time` with `Date()`. More than 120 s off: the start is blocked with
"Set your Mac's date and time to automatic (System Settings > General > Date & Time)".

## Resume after a crash needs approval (S3 / M3)
- Exam setting `resume_needs_approval: bool`, default **true**, in ExamIn/exam_out and the
  editor ("Teacher approves a student coming back after FairPlay closed").
- Attempt columns `pending_resume: bool` (default false) and `pending_since: datetime|null`.
- When a start resumes an in-progress attempt **from a new app run** (the session rotates in
  `_resume`; a plain page reload must not trigger it), and the exam setting is on:
  - set pending, record event `resume_requested`;
  - the start response carries `"needs_approval": true`.
  The server agent must read `_resume` and document exactly which case this is.
- While pending:
  - `app-beat` and `GET /attempts/{aid}` return `"approval": "pending"`.
  - Answers PUTs are still accepted, so no work is lost.
  - The page shows "Wait for your teacher" instead of questions.
- `POST /api/exams/{id}/attempts/{aid}/approve-resume` (teacher):
  - clears pending;
  - extends `deadline_at` by the time spent waiting, capped at 15 minutes;
  - records event `resume_approved` with the minutes added.
  - After that, beats and the attempt view return `"approval": "approved"`.
- Live room: a "Waiting for approval" badge plus an **Approve** button.

## Device swap (S4 / M3)
- Start on a second device while the attempt is bound elsewhere:
  `409 {"detail": {"code": "swap_needed", "message": <today's OTHER_DEVICE_DETAIL text>}}`.
  Every web caller that reads `detail` as a string must handle the object form too.
- `POST /api/student/attempts/{aid}/swap-request` body `{device_id}` (student auth, owner
  only) → `202 {ok:true}`. Records the requesting device and event `swap_requested`.
- `POST /api/exams/{id}/attempts/{aid}/approve-swap` (teacher):
  - does what `release-device` does today (device_id = None, new session, clear the cache);
  - records `swap_approved` and keeps `swap_old_session` and `swap_approved_at`.
- The new device keeps calling start every 5 s and binds normally once approved.
- Old device:
  - Its next beat, save or handin check gets the existing session error.
  - The handin check returns `{"status": "moved"}` for an attempt whose old session was
    swapped away. The Mac already treats unknown or other statuses carefully; it shows
    "This exam moved to another computer" and unlocks.
  - For 120 s after approval, one `PUT /answers` with the old session is accepted. It only
    merges questions the new device has not saved since the approval.
- After `deadline_at + LATE_GRACE`, swap-request and approve-swap return 409 "Finish on the
  computer you started on".
- Live room: a "Wants to continue on another computer" badge plus **Approve swap**.
  "Release device" stays.

## Sealed offline submit (S5 / M4)
- Bridge: the page sends `{action:"seal", attempt_id, answers_json, client_seq}` when the
  submit at time-up fails (offline). `answers_json` is the exact JSON string of the answers.
- The app seals and writes `Application Support/FairPlay/sealed/<attempt>.json` (mode 0600):
  `{payload, answers_json, proof}`.
  - `payload` = `attempt_id|session|device_id|client_seq|sealed_at|answers_sha256`.
  - `sealed_at` is ISO UTC with ms, ending Z. It is computed as last server time plus
    monotonic elapsed time (systemUptime).
  - `answers_sha256` = lowercase hex SHA-256 of the UTF-8 bytes of `answers_json`.
  - `proof` = lowercase hex HMAC-SHA256(offline key for that attempt and session, payload).
  - The offline key is the one from `offline-key`, i.e. `ac.offline_key(secret, aid, session)`.
  - The app answers `{type:"sealed", attempt_id, ok:true}`.
- `POST /api/student/attempts/{aid}/sealed-submit` (student auth, owner; **no session header
  required**, because the session may since have been rotated). Body: `{payload, answers_json, proof}`.
  - Parse the payload, check the attempt id matches, recompute the HMAC with the session from
    the payload, and compare in constant time.
  - Check the SHA-256 of `answers_json`.
  - `sealed_at` must lie between `started_at` and now + 2 min.
  - Saved as of `sealed_at`: if it's at most `deadline_at + LATE_GRACE`, the answers are graded
    as the final answers. Otherwise they go to `late_answers` and the attempt is flagged
    `late_sealed`, exactly like the existing late handling in submit.
  - Submits the attempt if it's still in progress.
  - Idempotent: the same payload again returns the same receipt.
  - Records event `sealed_submit` (device id, sealed_at). **It always goes to the teacher's
    review list**, because the key lives on the student's computer and a determined student
    could extract it.
  - Response `{ok:true, receipt, late_sealed:bool}`.
- At launch, the app uploads every sealed file before anything else and deletes a file only
  after a 200, or a 4xx other than 429. A 4xx keeps a copy under `sealed/rejected/` and logs it.
- Beat summary key `sealed=1` while a sealed file is pending. The live room shows "submission
  pending on this student's computer".
- Page at time-up, if the submit fails, offers three buttons:
  - **Try again now**
  - **Submit later from this computer**: after `sealed`, it shows "Your answers are sealed on
    this computer. Ask the invigilator to end the exam" plus the existing offline exit code
    flow.
  - **Ask the teacher for help**: shows the PC code.

## Require the strongest lock (S6)
- Exam `require_strong_lock: bool`, default false. Editor toggle: "Require the strongest lock
  (Windows: separate exam desktop. Mac: needs Apple assessment mode, not available yet)".
- The beat summary may carry `sep=0|1`. When the setting is on and a beat says `sep=0` (or no
  `sep` key), record event `weak_lock` once per attempt and show a live-room badge.
- The Mac today never sends `sep`, so Mac students show as weak; that is intended and
  matches the editor text.

## Additions (2026-10-20, Mac side)
- The bridge `state` message also carries `app_version`, `platform` ("mac") and `sealed_pending` (bool).
- When `state.sealed_pending` is true and the student is signed in, the page posts
  `{action:"sealedToken", token}` once per page load. Student tokens last 8 h, so the app may
  have no valid token at its next launch.
- sealed-submit on an attempt that is already submitted:
  - same answers → 200 with the existing receipt;
  - different answers → `409 {"detail":{"code":"already_submitted"}}` plus a `sealed_submit`
    review event for the teacher.
- The hand-in check for a session that was swapped away (or released by the teacher) returns
  status `moved`, signed with the session the request came with.
- Preflight on the Mac also calls `GET /api/app/version` (falling back to `/api/health`) to
  read the server time and the minimum version, and answers the page within 2.5 s.
